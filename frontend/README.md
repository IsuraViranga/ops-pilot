# OpsPilot Web Portal

Next.js 16 enterprise portal. In Phase 0 it renders live backend health; from Phase 1 it
becomes the ticketing, approvals and admin interface.

| | |
|---|---|
| Framework | Next.js 16 (App Router), React 19 |
| Language | TypeScript, strict |
| Styling | Tailwind CSS 4 |
| Quality | ESLint, Prettier, `tsc --noEmit` |

---

## Running it

```bash
cp .env.example .env.local
npm install
npm run dev          # http://localhost:3000
```

The backend should be running, though the page degrades gracefully if it is not:

```bash
cd ../deployment/docker && docker compose up -d
cd ../../services/platform && ./mvnw -pl platform-app spring-boot:run
```

## The browser never calls Spring directly

```
Browser  ──►  /api/health  ──►  Spring /actuator/health
             (Next.js route handler)
```

This indirection is the point, not an accident.

| Reason | Detail |
|---|---|
| **No CORS** | The browser request is same-origin. The backend never has to trust a browser origin, and there is no preflight configuration to get wrong |
| **Actuator stays private** | In production the management endpoints are not exposed to the internet at all. Only this route is |
| **Nothing leaks** | Actuator returns disk paths, database vendor, driver versions and Redis version. The route passes on component names and statuses, nothing else |
| **One place for auth** | When the portal becomes authenticated, the session check lives here rather than in every component |

This is the backend-for-frontend pattern, and it is how the rest of the API will be
consumed as the application grows.

Verified: with the backend up, `/api/health` returns

```json
{"status":"UP","components":[{"name":"db","status":"UP"},{"name":"redis","status":"UP"}, ...]}
```

and contains none of Actuator's `validationQuery`, file paths or version strings.

## Configuration

| Variable | Default | Notes |
|---|---|---|
| `OPSPILOT_API_URL` | `http://localhost:8080` | Where Spring is listening |

**No `NEXT_PUBLIC_` prefix, deliberately.** A `NEXT_PUBLIC_` variable is inlined into the
JavaScript bundle and is readable by anyone who opens devtools. The backend address is
internal, so it stays server-side. In Kubernetes it becomes an in-cluster service name such
as `http://platform.opspilot.svc.cluster.local:8080`, which is not resolvable from a browser
at all.

## Structure

```
src/
├── app/
│   ├── api/health/route.ts   # BFF proxy to the backend
│   ├── layout.tsx
│   └── page.tsx              # server component - fetches health for first paint
├── components/
│   ├── HealthPanel.tsx       # client component - polls every 5s
│   └── StatusBadge.tsx
└── lib/
    └── health.ts             # types and the server-side fetch
```

**Server components by default.** Only `HealthPanel` is a client component, because it
needs `useState` and an interval. Everything else renders on the server, so the first paint
already contains real data rather than a spinner.

## Behaviour when the backend is down

The page still returns HTTP 200 and renders; the panel shows `Unreachable` with the
commands needed to start the backend. `/api/health` returns HTTP 503, matching Actuator's
own convention so an uptime check sees a failure without parsing the body.

A dashboard that crashes when the thing it monitors is down is not a monitoring dashboard.
